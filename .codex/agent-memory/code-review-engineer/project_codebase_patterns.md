## Established Conventions

- All domain models use Java `record` types (immutable value objects), not JPA entities.
- Repository interfaces use plain Spring JDBC (`JdbcTemplate`), not JPA. SQL belongs in the implementing class, not scattered elsewhere.
- All timestamps use `java.time.Instant` (UTC) in domain models. `CalendarEvent.startTimeUtc` / `endTimeUtc` naming convention makes UTC intent explicit.
- Package structure is feature-vertical: `auth/`, `calendar/`, `calendar/sync/`, `availability/`, `booking/`, `workinghours/`, `email/`, `config/`.
- Stub classes use `// Implemented in TASK-XXX` comment pattern; these are intentional scaffolding, not incomplete work.
- `DataSourceConfig` is a hand-rolled HikariCP datasource bean that overrides Spring Boot's autoconfiguration. It must always set `maxPoolSize=1` (SQLite write-lock constraint).

## Known Risks and Watch Points

- **HikariCP `connectionInitSql` with SQLite**: HikariCP executes `connectionInitSql` via `Statement.execute()`, which in the SQLite JDBC driver does NOT support multiple semicolon-separated statements. Only the first PRAGMA will execute. Always use separate `connectionInitSql` calls or a `SQLiteDataSource` subclass approach.
- **Flyway + SQLite**: Spring Boot 3.3+ pulls Flyway 10+. As of Flyway 11.7.2, SQLite support IS bundled in `flyway-core` (classes in `org.flywaydb.core.internal.database.sqlite`). No extra `flyway-database-sqlite` artifact is needed. Verify on each major Spring Boot version bump.
- **Encryption default fallback**: `encryption.secret-key=${ENCRYPTION_SECRET_KEY:dev-secret-key-change-in-production}` in `application.properties` provides a weak plaintext default. While acceptable for dev scaffold, the production deploy must override this via environment variable.
- **Session cookie `secure` flag**: `server.servlet.session.cookie.secure=true` IS set in `application.properties` (added in TASK-005 admin-auth-BE branch). `application-local.properties` correctly overrides it to `false` for local dev. `same-site=strict` and `http-only=true` are also configured. This risk is now resolved at the property level.
- **`Booking.status` as `String`**: `Booking.status` still uses `String` instead of an enum. `CalendarAccount.provider` was promoted to a `Provider` enum as of the design-review pass. Flag any code that string-compares booking status values — these should eventually move to an enum.
- **`@ExceptionHandler(Exception.class)` catch-all intercepts Spring MVC's own resolvers** — `ExceptionHandlerExceptionResolver` runs before `ResponseStatusExceptionResolver` and `ResponseStatusExceptionResolver`. Adding a catch-all `@ExceptionHandler(Exception.class)` to a `@RestControllerAdvice` will intercept `ResponseStatusException` (thrown by controllers for intentional 400/404/409) and return 500 instead of the intended status. Always add an explicit `@ExceptionHandler(ResponseStatusException.class)` that propagates `ex.getStatusCode()`. Similarly, Spring 6.2 throws `HandlerMethodValidationException` (not `MethodArgumentNotValidException`) for `@Valid` on record method parameters — the old `MethodArgumentNotValidException` handler is never invoked. Spring 6.1+ throws `NoResourceFoundException` (not `NoHandlerFoundException`) for unmatched static resource paths. Any future addition of a catch-all must audit and add explicit handlers for all three, or it will silently swallow them as 500.
- **`WorkingHours` uses `String` for `startTime`/`endTime`**: Confirmed intentional design (TASK-010). The task spec mandates `String` stored as `HH:MM` local time. `WorkingHoursService.validate()` enforces the format with a regex (`^([01]\\d|2[0-3]):[0-5]\\d$`). Type-safety risk is fully accepted at this layer; no `LocalTime` migration is planned for MVP.

## Auth Layer Patterns (established in TASK-005, reviewed 2026-06-11; updated 2026-06-26)

- `AuthController` holds a direct `AdminRepository` reference to serve `GET /auth/me`. This is a mild SRP bend — the controller owns two distinct collaborators (service + repo). Acceptable for MVP but flag if the controller grows.
- `AuthService.signup()` validates slug format but does NOT check slug uniqueness before insert. Uniqueness is enforced only by the database `UNIQUE` constraint, which surfaces as an unhandled `DataIntegrityViolationException` (500) instead of a user-friendly 409/422.
- `EmailAlreadyUsedException` message includes the raw email value (`"Email already in use: " + email`). This is a minor info-disclosure item in high-sensitivity deployments.
- `JdbcAdminRepository.save()` re-queries by email after INSERT to return the fully populated entity. This is a safe but slightly redundant pattern (two round-trips); using `findById(keyHolder.getKey().longValue())` would be more direct and avoid the theoretical ambiguity of a just-inserted duplicate email.
- `keyHolder.getKey()` is called without a null check in `JdbcAdminRepository.save()` — `getKey()` returns `null` when SQLite JDBC does not populate the `GeneratedKeyHolder`. This will NPE in the rare case of a driver/config mismatch.
- `SessionUtils.requireAdminId()` uses an unsafe raw cast `(Long)` — if anything ever stores a non-Long value under `"adminId"`, it will throw `ClassCastException` and produce a 500 instead of 401.
- `@DirtiesContext(AFTER_EACH_TEST_METHOD)` is used for integration test isolation with in-memory SQLite. Correct approach; avoids shared state between tests at the cost of Spring context reload per test (slow at scale).
- Test `signupUser()` helper discards the `MvcResult` and does not assert status — silently swallows signup failures, which can cause misleading test failures downstream.

## OAuth / Token Patterns (established in TASK-007 google-auth; extended in TASK-008 outlook-auth; reviewed 2026-06-15)

- `GoogleOAuthService` uses a stateless HMAC-SHA256 state parameter (`adminId:base64url(HMAC(adminId, derivedHmacKey))`) for CSRF prevention. The HMAC key is domain-separated from the AES key: `SHA-256("oauth-state-hmac:" || rawKey)` vs `SHA-256(rawKey)`. Both consumers still derive from the same `encryption.secret-key` — acceptable MVP trade-off, should be split into independent secrets in production.
- `EncryptionService` uses AES-256-GCM with a random 12-byte nonce prepended to the ciphertext, base64-encoded. Key is derived via `SHA-256(rawKey)`. Output format: `base64(nonce || ciphertext+GCM_tag)`. Standard and sound.
- **`SecureRandom random = new SecureRandom()` as an instance field** in `EncryptionService` is correct and thread-safe. `SecureRandom` is thread-safe by spec.
- **`SessionAuthFilter`** promotes the custom `adminId` session attribute to an `AdminAuthentication extends AbstractAuthenticationToken` before `AnonymousAuthenticationFilter`. `AdminAuthentication.getPrincipal()` returns the `adminId` as a `Long`. Using a custom token type instead of `UsernamePasswordAuthenticationToken` avoids null-credentials warnings in debug logs and makes the principal type unambiguous. Any code casting `Authentication.getPrincipal()` to get the admin ID must cast to `Long`, not `UserDetails` or `String`. `/calendar/google/connect` and `/calendar/outlook/connect` are protected at two independent layers: Spring Security filter chain (401 before controller runs) and `SessionUtils.requireAdminId()` inside the controller. Both callback endpoints remain in `permitAll()` — secured by the HMAC-signed state parameter instead of a session.
- **`FilterRegistrationBean` with `setEnabled(false)`** in `SecurityConfig` prevents Spring Boot from registering `SessionAuthFilter` a second time in the servlet filter chain (it is already registered inside the Spring Security chain via `addFilterBefore`). Without this, the filter runs twice per request.
- **`GoogleIdTokenVerifier`** is built once in the `GoogleOAuthService` constructor (stored as a field) and reused across requests. It verifies signature using Google's public keys (fetched lazily from `accounts.google.com/oauth2/v3/certs` and cached), audience (must equal `clientId`), issuer (`accounts.google.com`), and expiry. `verify()` returns `null` on any failure — the code checks for null and throws. Do not regress to `tokenResponse.parseIdToken().getPayload()` which skips all cryptographic checks.
- **`ON CONFLICT DO UPDATE SET` upsert** in `JdbcCalendarAccountRepository.insert()` performs an in-place update, preserving `id`, `is_primary`, and `connected_at`. A subsequent `SELECT` returns the canonical row. This replaces the prior `INSERT OR REPLACE` pattern which was a DELETE+INSERT that changed the rowid, cascaded FK deletions, and silently reset `is_primary` to `false` on reconnect.
- **Refresh token null guard**: `GoogleOAuthService.handleCallback` throws `IllegalStateException` when Google omits the refresh token (e.g., reconnect without revoking). This prevents silently overwriting a valid stored refresh token with an empty encrypted string.
- **`JdbcCalendarAccountRepositoryTest`** uses `@MockBean GoogleOAuthService` and `@MockBean GoogleTokenRefresher` because `GoogleIdTokenVerifier` attempts to fetch Google's JWKS endpoint during `GoogleOAuthService` construction — this fails without network access in tests. `OutlookOAuthService` and `OutlookTokenRefresher` make no HTTP calls during construction and do NOT need mocking in the same test.
- **`GoogleTokenRefresherTest`** uses a `@TestConfiguration @Bean @Primary MockHttpTransport` that returns a canned JSON token response, replacing the production `NetHttpTransport` bean. Requires `@SpringBootTest(properties = "spring.main.allow-bean-definition-overriding=true")` because `@TestConfiguration` beans are registered after production beans and overriding is disabled by default.
- **`HttpTransport.buildRequest` is `protected`** — cannot be stubbed with Mockito from outside `com.google.api.client.http` (compile-time error). Always use the `MockHttpTransport` + `MockLowLevelHttpRequest` pattern from `google-http-client-test` for intercepting Google API calls in tests.
- **`docker compose restart` does not recreate containers** — new environment variables added to `.env` or `docker-compose.yml` are not picked up until the container is recreated with `docker compose up -d --force-recreate <service>`. Use `docker compose exec <service> env | grep VAR` to verify env vars are present before debugging property-binding issues.
- **`APP_BASE_URL` is hardcoded in `docker-compose.yml`** (`APP_BASE_URL: http://localhost`) because it is not a secret and its value is fixed for the Docker deployment context. Do not move it to `.env` — `env_file` values require container recreation, not just restart, to take effect.
- **`sqlite3` CLI is not installed in the backend container image** (JRE-only base). Query the database from the host using the mounted volume path `./data/unified-calendar.db`. Never add `sqlite3` to the container image — it serves no runtime purpose.

### Outlook OAuth Patterns (TASK-008, 2026-06-15)

- **`MicrosoftClientConfig` provides a named `RestClient` bean (`"microsoftRestClient"`)** rather than using the auto-configured prototype `RestClient.Builder` directly. Services inject it as `@Qualifier("microsoftRestClient") RestClient`. The named bean is necessary so test configurations can override it with `@Bean(name = "microsoftRestClient") @Primary` without affecting any other RestClient consumers. Never replace this with an anonymous `@Autowired RestClient.Builder` built inline in the service constructor — that breaks the `MockRestServiceServer` override seam used in `OutlookTokenRefresherTest`.
- **`OutlookTokenRefresherTest` `MockRestServiceServer` pattern**: a `@TestConfiguration` inner class provides `@Bean(name="microsoftRestClient") @Primary RestClient` that calls `MockRestServiceServer.bindTo(builder).build()` inside the factory method and stores the server as a `static` field on the config class. Because `@DirtiesContext(AFTER_EACH_TEST_METHOD)` recreates the Spring context for each test, the factory method is called again per test and the static field is refreshed. Tests access the server via `MockRestClientConfig.mockServer`. This is the correct pattern for intercepting `RestClient` calls in Spring Boot 3.2+ (`MockRestServiceServer.bindTo(RestClient.Builder)` requires Spring Framework 6.1+).
- **`OutlookOAuthService.buildState` and `validateState` are package-private** (no access modifier), unlike the corresponding private methods in `GoogleOAuthService`. This is a deliberate testability choice: `OutlookOAuthServiceTest` calls them directly to test HMAC logic and malformed-state edge cases without needing HTTP stubs. If they are ever made private, those unit tests will fail to compile.
- **`microsoft.tenant-id` is guarded at two levels**: `application.properties` defaults to `common` via `${MICROSOFT_TENANT_ID:common}`, and both `OutlookOAuthService` and `OutlookTokenRefresher` constructors apply `tenantId.isBlank() ? "common" : tenantId`. The constructor guard covers the edge case where `MICROSOFT_TENANT_ID` is explicitly set to an empty string in the environment. Without the guard, token endpoint URLs collapse to `https://login.microsoftonline.com//oauth2/v2.0/token` (double slash) which Microsoft rejects with 400.
- **Outlook `mail` field can be null for personal Microsoft accounts**. `OutlookOAuthService.handleCallback` falls back to `userPrincipalName` when `mail` is null or blank. Work/school accounts (Entra ID) populate `mail`; personal accounts (`@outlook.com`, `@hotmail.com`) may return `null` for `mail`. Never store the email without this fallback — a null email stored as null in the DB will break display and lookup logic downstream.
- **`OutlookTokenRefresher` DOES persist the new refresh token when Microsoft returns one (rolling token policy)** — the new refresh token is encrypted and saved; the existing token is retained when the response omits a new one. Both `OutlookTokenRefresherTest.refreshPersistsNewRefreshToken` and `refreshPreservesRefreshToken` cover these branches.
- **`OutlookOAuthService.handleCallback` DOES guard against a null refresh token** — `IllegalStateException` is thrown with an actionable message before `encryptionService.encrypt` is called. `OutlookOAuthServiceCallbackTest.handleCallback_throwsWhenRefreshTokenAbsent` verifies this. (Previous KB entry incorrectly flagged this as missing — resolved in final implementation.)
- **`SCOPE` constant is package-private (`static final`, no `public`)** in `OutlookOAuthService`. `OutlookTokenRefresher`, in the same package, references it as `OutlookOAuthService.SCOPE`. This is NOT duplication — there is a single canonical definition. No extraction to a separate class is needed unless the classes ever move to different packages.
- **`SecurityConfigTest` covers all three new protected endpoints added in TASK-008**: `DELETE /calendar/accounts/{id}` (401 without session), `PUT /calendar/primary` (401 without session), and `GET /calendar/accounts` (401 without session). `GET /calendar/outlook/connect` (the fourth new endpoint) is NOT explicitly tested in `SecurityConfigTest` — it relies on Spring Security's `anyRequest().authenticated()` default catch-all, which covers it. Consider adding an explicit test for future clarity.
- **`application-test.properties` lacks `microsoft.client-id` and `microsoft.client-secret`**. These default to empty string (`${MICROSOFT_CLIENT_ID:}`) in `application.properties`, which is acceptable for tests since the services only use them in HTTP calls (which are mocked). However, if a future test omits the MockBean/RestClient mock, the service will construct successfully but fail at runtime with a misleading error. Document this constraint. [FLAGGED as Minor issue in TASK-008 review 2026-06-15]
- **`DELETE /calendar/accounts/{id}` returns 204 even if the account does not exist**. `repository.delete(id, adminId)` is a scoped `DELETE WHERE id=? AND admin_id=?` with no existence check — a missing or foreign-owned account is a silent no-op. This matches the task spec but can surprise callers expecting 404 on missing resources.
- **`PUT /calendar/primary` is not fully atomic across its three DB operations**. The controller does `findById` (existence check) → `setPrimary` (two `@Transactional` UPDATEs) → `findAllByAdminId` (read back). `setPrimary` itself is atomic, but the check-then-act between `findById` and `setPrimary` is not. A concurrent delete between those two steps would cause `setPrimary` to silently affect zero rows with no error. Acceptable for MVP single-admin use; flag if concurrent-session scenarios arise.

## Working Hours API (TASK-010, implemented 2026-06-21)

- **`@Transactional` on `JdbcWorkingHoursRepository.replaceAll` is the first use of `@Transactional` in this codebase.** Other repositories omit it because their operations are single statements. `replaceAll` needs it because DELETE + batch INSERT must be atomic. Spring Boot auto-configures a `DataSourceTransactionManager` for HikariCP, so no extra config is needed. The `maxPoolSize=1` constraint (SQLite write-lock) means there is no connection-deadlock risk from nested transactions on the same thread. If `maxPoolSize` is ever raised, revisit.
- **Transaction boundary is at the repository level, not the service level.** `WorkingHoursService.saveWorkingHours` calls `replaceAll` (transactional) and then `getWorkingHours` (a separate non-transactional read). The PUT response is the re-read state, which is outside the transaction — a concurrent replacement between those two calls would theoretically produce a misleading response body. Harmless in single-admin/single-connection MVP; flag if multi-session scenarios arise.
- **Time ordering uses lexicographic `String.compareTo`, not `LocalTime.isBefore`.** `dto.startTime().compareTo(dto.endTime()) >= 0` is correct only because `HH:MM` zero-padding preserves sort order. If format validation were ever relaxed (e.g., accepting `9:00`), this comparison would silently break without throwing. Any future change to `TIME_PATTERN` must verify the comparison still holds.
- **Missing `dayOfWeek` in the JSON body is rejected with 400.** `WorkingHoursDto.dayOfWeek` is an `Integer`, so Jackson deserializes a missing key as `null`; `WorkingHoursService.validate()` throws `ValidationException("dayOfWeek is required")`.
- **`PUT /working-hours` with a JSON body of literal `null` returns 400.** Jackson deserializes the literal `null` as a Java `null` list; `WorkingHoursService.validate()` guards `dtos == null` and throws `ValidationException("Request body must not be null")`.
- **Pre-existing flaky test: `OutlookOAuthServiceTest.validateState_rejectsTamperedHmac`** fails when the full suite is run (`./mvnw test`) but passes in isolation (`-Dtest=OutlookOAuthServiceTest`). Root cause is shared Spring Security context state between test classes (test ordering artifact). Not introduced by TASK-010. Do not investigate this failure in the context of working-hours changes.

## Calendar Sync Engine (TASK-012, implemented 2026-06-22; updated 2026-06-26)

- **`CalendarAccountRepository.findAll()` has no admin scoping** — intentionally returns all accounts across all admins for the scheduler. This is not an auth bypass; the method is only called from `CalendarSyncService.syncAll()`. Any future caller that uses it in an HTTP handler must scope by `adminId`.
- **Token is refreshed unconditionally before every sync cycle** — `CalendarSyncService` calls `GoogleTokenRefresher` or `OutlookTokenRefresher` before each `fetchEvents` call, not lazily on a 401. This adds one OAuth token-endpoint round-trip per account per 5-minute cycle. At small account counts this is fine; at scale, add lazy refresh on provider 401.
- **`GoogleSyncAdapter` uses a bearer-token-only `HttpRequestInitializer` lambda** (`request -> request.getHeaders().setAuthorization("Bearer " + accessToken)`) instead of the deprecated `GoogleCredential`. This is the correct modern pattern. Do not regress to `GoogleCredential`.
- **`normalize()` returns `null` only for all-day events** in both adapters (no `dateTime` in the start/end fields). Recurring event instances — `occurrence` and `exception` in Outlook, instances with `recurringEventId` in Google — are intentionally included because both APIs provide stable per-occurrence IDs (`calendarView` and `setSingleEvents(true)` expand series into instances before returning). The availability engine requires recurring busy blocks; filtering them out would show occupied slots as free. Do not re-add a recurring-instance filter. Callers check `if (normalized != null)`. Do not replace with `Optional` unless the whole codebase adopts it.
- **`upsert()` `ON CONFLICT DO UPDATE SET` deliberately excludes `is_booking_event`** — sync-originated upserts must not overwrite the flag set by the booking flow. The conflict clause updates only `title`, `start_time_utc`, `end_time_utc`, `provider_updated_at`, and `last_synced_at`. Any future column added to the schema must be explicitly included or excluded from the UPDATE SET with intentional reasoning.
- **`deleteByCalendarAccountIdAndProviderEventIdNotIn` with an empty list deletes ALL events for the account** — correct behavior (provider returned nothing in the window → purge the local cache). The empty-list branch runs a simpler `DELETE WHERE calendar_account_id = ?` because `NOT IN ()` is invalid SQL. Do not add a `isEmpty()` guard that skips the delete entirely — that would leave stale events indefinitely.
- **Dynamic `NOT IN` placeholder string** in `deleteByCalendarAccountIdAndProviderEventIdNotIn` is built at runtime (`"?, ?, ?"` joined by commas). Safe from SQL injection because the list contains only provider event IDs from the provider API response, not user-controlled input. If the list ever grows to thousands of IDs, consider chunked batch deletes.
- **Outlook `startDateTime`/`endDateTime` lack a Z suffix when `Prefer: outlook.timezone="UTC"` is sent** — Graph returns values like `"2024-01-01T09:00:00.0000000"` (no trailing Z). `LocalDateTime.parse(str).toInstant(ZoneOffset.UTC)` is correct. Do NOT use `Instant.parse()` on these fields — they have no Z suffix and will throw `DateTimeParseException`.
- **Outlook `lastModifiedDateTime` DOES have a Z suffix** — use `Instant.parse()` on this field, not `LocalDateTime.parse()`. The two fields require different parsers in the same event object.
- **`updateLastSyncAt()` is a surgical single-column UPDATE** — `CalendarSyncService` calls `calendarAccountRepository.updateLastSyncAt(id, Instant.now())` on success and `updateLastSyncAt(id, null)` on token-refresh failure. It does NOT call `save()` with the full account object. This is critical: `save()` would overwrite `encrypted_refresh_token` with the value from the in-memory `CalendarAccount` record, silently discarding any rotated refresh token that `OutlookTokenRefresher` already persisted to the database (Microsoft rolling-token policy). If `save()` is ever used here again in a future refactor, it WILL break Microsoft token rotation silently.
- **Microsoft Graph 401 with no body on `/me/calendarView` means the account has no Exchange Online mailbox** — this is NOT an authentication failure. A token can be fully valid (correct `aud`, `scp`, `tid`) and still get a 401 with an empty response body on this endpoint if the mailbox doesn't exist. The fix is to use `MICROSOFT_TENANT_ID=common` and connect a personal Outlook.com or Hotmail account (which always has Exchange Online). Work/school accounts in Entra ID tenants that do not have Microsoft 365 licenses also hit this. Do NOT debug a 401-no-body by rotating credentials or changing scopes — check mailbox existence first.
- **Both adapters log raw-fetched and kept event counts at INFO level** — `"Google Calendar fetched N raw event(s), kept M for account A (all-day events skipped)"` and the Outlook equivalent. If `M < N`, all-day events are being skipped (expected). If `N = 0`, the calendar is genuinely empty in the sync window or the API returned nothing. These log lines are the first diagnostic signal when `calendar_events` is empty after a successful sync.
- **`CalendarSyncService.syncAccount` logs the final count at INFO level** — `"Synced N event(s) for account A (PROVIDER)"`. This supersedes the prior `log.debug` call. The INFO-level log is essential for diagnosing sync behavior without enabling DEBUG globally.
- **Token refresh failure calls `markSyncFailed(id, errorMessage)`** — writes `NULL` to `last_sync_at` AND the error string to `last_sync_error`. On success, `updateLastSyncAt(id, Instant.now())` writes only `last_sync_at`; it does NOT clear `last_sync_error`. This means a previously failed account will retain its error message in the DB even after a subsequent successful sync if only `updateLastSyncAt` is called. A provider API error (5xx, non-token) logs and skips without touching either column. Both paths continue processing subsequent accounts.
- **`Provider` enum + `SyncAdapter` dispatch** — `CalendarAccount.provider` is now `Provider.GOOGLE` / `Provider.OUTLOOK`. `CalendarSyncService` holds a `List<SyncAdapter>` and dispatches by calling the first adapter that returns `supports(provider) == true`. Adding support for a new provider requires only implementing `SyncAdapter` and registering it as a Spring bean — no changes to `CalendarSyncService` needed. Failing to add a `supports()` implementation that returns `true` for the new `Provider` value will silently skip all accounts of that type.
- **`TokenRefreshResult(String accessToken, CalendarAccount updatedAccount)` contract** — token refreshers return the decrypted access token and the updated `CalendarAccount` record (with the new encrypted token), but do NOT persist to the DB themselves. `CalendarSyncService.syncAccount` decides what to persist. A caller that ignores the returned `updatedAccount` will silently use a stale access token for the API call without corrupting the DB. Any future caller of a token refresher must handle the returned result — do not add DB persistence inside the refresher.
- **`CalendarSyncServiceTest` is a pure unit test** (no `@SpringBootTest`, plain Mockito) — all collaborators mocked including both adapters and both token refreshers. Constructor signature: `(calendarAccountRepository, calendarEventRepository, googleTokenRefresher, outlookTokenRefresher, List.of(googleSyncAdapter, outlookSyncAdapter))`. Both adapter mocks must have `supports()` stubbed (`when(googleAdapter.supports(Provider.GOOGLE)).thenReturn(true)` etc.) or the dispatcher skips all accounts silently. Integration coverage lives in `JdbcCalendarEventRepositoryTest` which uses `@SpringBootTest @ActiveProfiles("test")` with an in-memory SQLite database.
- **`JdbcCalendarEventRepositoryTest` mocks `GoogleOAuthService` and `GoogleTokenRefresher`** — same reason as `JdbcCalendarAccountRepositoryTest`: `GoogleIdTokenVerifier` attempts network access during construction. `OutlookOAuthService` and `OutlookTokenRefresher` do NOT need mocking (they make no HTTP calls on construction). Note: `OutlookTokenRefresher` injects `@Qualifier("microsoftRestClient") RestClient` which also requires network; the test omits this mock, relying on the bean being constructable without network access. Verify this holds if the `RestClient` bean configuration ever makes HTTP calls at startup.
- **Both `GoogleSyncAdapter` and `OutlookSyncAdapter` wrap their API calls in try/catch and rethrow as `RuntimeException` with account context** — `OutlookSyncAdapter` wraps the entire `while (url != null)` loop. The caller (`CalendarSyncService.syncAccount`) catches any `Exception`. All error paths include the account ID for log correlation.
- **`ROW_MAPPER` in `JdbcCalendarEventRepository` calls `Instant.parse(rs.getString("last_synced_at"))` without a null guard** — `last_synced_at` has `NOT NULL DEFAULT` in the schema so this is safe, but it is fragile against schema changes. Compare with `parseInstant()` used for `provider_updated_at` (nullable). Any future column made nullable that is read via `Instant.parse` directly will NPE silently at runtime.
- **`OutlookSyncAdapter.logTokenClaims` decodes JWT payload to log `aud`/`scp`/`tid` at INFO** before each Graph call. These are non-secret token metadata fields safe to log. The log appears every 5-minute sync cycle per Outlook account — if this is too noisy at scale, gate it behind a DEBUG check or remove after the 401-diagnosis period ends.

## Development Environment — Docker Compose Mandate (established 2026-06-22)

- **Full-stack runs MUST use Docker Compose** — any workflow involving frontend, backend, and database together must go through `docker compose up`. Running `./mvnw spring-boot:run` from `backend/` creates `backend/data/unified-calendar.db`, which is a completely separate SQLite file from the Docker volume at `data/unified-calendar.db` (project root). Calendar accounts, events, and all persistent state become invisible between the two modes.
- **`backend/data/` must never exist** — delete it immediately if it appears. The canonical database path is `data/unified-calendar.db` (project root), mounted via Docker volume `./data:/app/data`. If `backend/data/unified-calendar.db` is ever checked in or left on disk and then the backend is started locally via Maven, Flyway will apply migrations to the wrong file, creating a silent divergence.
- **Flyway checksum mismatch is a symptom of the two-database problem** — if `./mvnw spring-boot:run` fails with a Flyway checksum error, the most likely cause is that a migration file was edited after being applied to `backend/data/unified-calendar.db`. The fix is to delete `backend/data/` entirely, not to repair the Flyway baseline. Never run `flyway repair` on `backend/data/` — it masks the real problem.
- **Backend-only Maven runs are allowed** only when working on backend unit/integration tests without a browser. Always use `-Dspring-boot.run.profiles=local` to pick up `application-local.properties`. Be aware that this run creates `backend/data/` — clean it up afterward.
- **New Docker environment variables require container recreation**, not restart — `docker compose restart` does NOT pick up changes to `.env` or `docker-compose.yml`. Use `docker compose up -d --force-recreate <service>` after any env var change.

## Calendar Events API (TASK-013, reviewed 2026-06-24; updated 2026-06-26)

- **Jackson record serialization preserves "is" prefix for boolean components** — `CalendarAccountResponse.isPrimary` (existing, confirmed working via frontend `isPrimary` usage) proves that Jackson serializes boolean record components using the component name verbatim. Do NOT flag `isBookingEvent` or `isPrimary` as a "Jackson strips is prefix" risk — it does not apply to Java records in this version of Jackson.
- **`@Async` + `@Scheduled` on the same method** changes `fixedDelay` semantics: the delay timer starts from when the async Future is returned (immediately), not when the task completes. This effectively makes a `fixedDelay = 300_000` behave like `fixedRate = 300_000`. For MVP with few accounts this is low risk, but it does allow concurrent sync cycles if a single run exceeds 5 minutes. Flag in any future review of CalendarSyncService if account count grows.
- **`triggerSync` POST /calendar/sync delegates to `CalendarSyncer` interface** — the production implementation (`CalendarSyncService`) is `@Profile("!test")`; a `NoOpCalendarSyncer` bean is registered under `@Profile("test")` via `NoOpCalendarSyncConfig`. This eliminates `@Nullable @Autowired(required=false)` — the interface is always satisfied, no null guard in the controller. ## Availability Engine (TASK-015, reviewed 2026-06-27)

- **`IntervalUtils.subtract` does NOT sort its busy-interval input.** It is designed to receive already-merged (sorted, non-overlapping) intervals from `IntervalUtils.merge`. ## ICS Calendar Invites (TASK-021, implemented 2026-07-19)

- **Line folding is measured in UTF-8 octets, not Java characters** — RFC 5545 limits content lines to 75 octets, and continuation lines spend one octet on their leading space. `IcsService.fold()` therefore allows 75 bytes on the first physical line and 74 bytes of content on continuations while advancing by Unicode code point. Flag any refactor that uses `String.length()` or splits surrogate pairs, because non-ASCII visitor notes would then produce invalid or oversized lines.
- **The booking cancel token is the stable ICS UID for both confirmation and reschedule invites** — `EmailService` always passes `booking.cancelToken()` even though a separate reschedule token exists. Changing to the reschedule token or generating a new UID would cause calendar clients to create duplicate events instead of updating the existing event.
- **iCal4j is test-scoped compatibility evidence, not a runtime dependency or proof of proprietary-client behavior** — `IcsServiceTest` independently parses folded, escaped, non-ASCII output. Apple Calendar, Google Calendar, and Outlook import/update behavior must still be manually recorded in `doc/testing/ics-calendar-client-compatibility.md`; do not mark cross-client acceptance complete based only on parser success.
- **The TASK-021 `METHOD:REQUEST` template has no `ATTENDEE` field** — iCal4j parses the generated file but strict validation reports a required-attendee error for a meeting request. The current `IcsService.generate` contract receives only the organizer address, so adding a valid attendee requires an intentional signature and call-site change to pass the visitor email. Flag any claim of strict RFC validation until that contract is resolved; do not silently invent an attendee or switch the task-mandated method.

### Known Bugs / Risks Found in TASK-006 FE Auth Review

- **`AuthContext.logout()` does not clear state when the backend call fails.** If `POST /auth/logout` returns a network error, `setAdmin(null)` and `navigate('/login')` are skipped, leaving the user stuck in an authenticated UI with a dead session. Use `finally` instead of sequential `await`.

In strict projects this will be a type error unless `lib` is set to `ES2022+` or a `// @ts-ignore` is used.
